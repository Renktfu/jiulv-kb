# 架构与取舍

## 数据怎么流

```
资料库目录（md/docx/pdf/xlsx/txt）
      │  jiulv connect：探测 WorkBuddy / OpenCLaw 两边的库，写 sources.yaml
      │  jiulv sync：按来源指纹判断要不要扫；jiulv watch 常驻轮询
      ▼
      │  jiulv ingest：只读扫描，按 mtime + 内容哈希做二次增量
      ▼
解析 → 元数据抽取 → 分块
      │
      ├── docs      一篇一行：标题、类型、地区、酒店、等级、赞藏评、原文
      ├── chunks    按标题切段，700 字上限，80 字重叠
      ├── hooks     「## H-xxx-001」块解析成结构化钩子
      ├── docs_fts / chunks_fts   FTS5 + 中文二元分词
      ├── annotations   每篇的「为什么这么写」，来自原文小节 / 采集点评 / 指标推算
      ├── concepts      地区、酒店、作者、系列、人群、痛点、钩子、手法
      └── doc_concepts  笔记 ↔ 概念的边表，双向链接就靠它
      ▼
检索（BM25 → 聚合到文档 → 去重 → 排序）
图谱（概念为中心取一跳子图，或概念共现全景）
      │
      ├── REST  /api/v1/*
      └── MCP   stdio，十一个工具
      ▼
组稿：规则 + 钩子 + 同地区爆款结构 + 可核对事实 → 一段带约束的提示词
      ▼
Agent / 人写稿 → 发布 → 回填数据（kb_feedback） → 回写进库（kb_save）
      │                                              │
      └────── 复盘哪类钩子有效 ────────────────────────┘
                  回写池 data/inbox 参与下一轮检索
```

## 连接层为什么不拷贝文件

两个 agent 的资料库就在本机磁盘上。可以定时 `rsync` 一份进项目目录，但那样立刻多两个问题：
版本分叉（源改了、副本没改）和双倍占用（115MB 的索引之外再放一份原文）。

所以只记路径，收录走增量。「文件是唯一真相」这句话在这里不是口号，是省掉一整类同步冲突的办法。

代价是库不能脱离本机搬走。真要迁移，`jiulv export` 出一份 jsonl，或者把 `data/kb.sqlite3` 拷过去一起拷。

判断「要不要重扫」的粒度是**来源指纹**，不是全库指纹：每个来源记（文件数, 总字节, 最新 mtime），
三元组一致就整段跳过。粗一点，但足够——真实场景里少扫一次不会错，多扫一次很贵（一万五千条注解要重算）。

## 回写为什么落成普通文件

回写接口（`POST /api/v1/inbox`）不往 `docs` 表里直接插一行，而是写一个 md 文件到
`data/inbox/inbox_<kind>/<日期>/`，再走一遍正常收录。这么做有三个好处：

一是单一入口。解析、元数据抽取、注解、图谱全走同一条流水线，回写内容不需要开特例，
也不会出现「接口写进去的文档没有注解」这种半成品状态。

二是可读可改。落盘就是纯 md，人可以打开改，改完下次同步会更新进库。数据库里的东西人改不动。

三是可撤销。删掉文件，下次同步会把它从库里回收，不会留一篇已经不存在的稿子。

代价是回写比直接 insert 慢一点（1888 篇的库，回写一篇约 1.5 秒，主要花在全库注解释重算上）。
考虑到写稿是分钟级操作，这个代价可以接受。

## 为什么是 SQLite

单文件、能拷走、能离线、并发读没问题。这个场景的数据量级是几千到几万篇，全文检索用 FTS5 足够，上 Postgres 或向量库属于给自己增加运维负担。

代价是写并发弱。当前实现是每次请求开一个连接，写入只发生在收录和回填，量很小，WAL 模式下不会互相卡。

## 为什么自己做中文分词

FTS5 自带两个能用的选择，都不合中文场景：

- `unicode61` 按空白和标点切，中文整段当一个词，「三亚」搜不到「三亚文华东方」里的内容。
- `trigram` 按三字符切，查询必须三个字符以上，「瑞吉」「柏悦」这种两字词直接搜不到。

所以自己做一层二元组：中文连续串切成相邻两字的所有组合，英文数字整段保留。建索引和查询用同一个函数，词表天然一致。不需要 jieba 那种词典，也没有新词漏切的问题。

代价是索引膨胀，实测 1500 篇 2100 万字原文，索引库 115MB，其中分词索引占大头。这个体量完全可以接受。

## 排序

BM25 打分，做三处调整：

标题命中单独一路召回，给 2.0 的固定加分，因为标题命中通常比正文命中更相关。

按类型加权。`index` 类文件（全量索引、素材清单）动辄列几百个标题，BM25 很容易被它带偏，乘 0.4；`daily` 0.7；`ops` 和 `misc` 0.85；其余 1.0。

按等级加权。S 级乘 1.25，A 级 1.12。爆款本身是质量信号。

## 为什么要去重

真实资料库里同一篇笔记常有三四份：主素材库一份，OpenClaw 每次导出一份，全量快照里还有一份。全都显示出来，前十条结果可能只有三个不同内容。

处理方式是结果层折叠：标题归一化后相同、且类型相同的，只保留分数最高的那份，其余计数。原始文件一个不删，路径照旧可查，只是不占版面。

按标题而不是按正文哈希，是因为不同来源的导出会带不同的头部字段，正文哈希必然不同，但标题通常一致。

## 组稿为什么拼提示词而不是直接生成

有三个原因。

一是可核对。返回的每个片段都带来源路径和入选理由，写完能对着原文逐条查。

二是模型无关。同一份提示词给 DeepSeek、Claude、本地模型都能用，不需要为每个模型写一套 prompt。

三是省钱。生成交给 Agent 自己做，服务端不重复调一次模型。

如果确实要服务端直出，`generation.enabled: true` 配好就能用，但对多数人没必要。

## 素材挑拣的顺序

组稿时素材不是按检索分数堆的，按可靠性排：

参考篇目先取同酒店，再取同地区按等级和评论数排，都不够才用关键词兜底。每条带 `reason` 说明来源。

规则只取标题或路径里带「规则」「手册」「风格」「模板」「原则」的，避免把范文误当规则塞进去。

事实只取类型是 `fact` 或 `guide` 的，同酒店优先。如果取到的是别家酒店的，提示词里会明确写「只参考写法，事实不能挪过来」。

钩子按人群命中、痛点命中、类型命中、是否已验证四级排序，最匹配的放前面。

## 上下文包的结构

七段，顺序有讲究：

任务、硬规则、风格规则、钩子、爆款结构、事实清单、输出要求。

硬规则放前面是因为模型对开头的指令更敏感。事实清单放后面，紧挨着输出要求，减少长上下文里被稀释。输出要求最后压一句「正文后列出事实出处」，逼模型自己完成一次核对。

## 注解为什么抽而不是生成

每篇笔记里其实已经写好了「为什么这么写」，只是没人把它当数据：文末常有 `#### 预订启示`、`#### 提取要点`，里面甚至有「写文案时：公区夸到顶，房间要有保留意见」这种直接写给下一位作者的话。采集记录里每条后面的长点评更是把「这篇价值在哪、哪儿不能当事实用」说得很清楚。

所以注解走抽取，不走生成。理由有两个：

一是可信。生成出来的「为什么好」听起来都对，但没法对账，写稿的人不敢用。抽出来的每条都能点回原文那一行。

二是免费。全库 1500 篇重算一遍注解只要一两秒，不需要模型、不需要联网、不需要 API Key。这也是它能默认开启的原因。

只有一类是算出来的：赞藏评比例。收藏是点赞两倍以上说明读者当资料存，评论超过点赞说明观点有对立面——这类判断写在 `origin='derived'` 里，界面上标「规则推算」，和原文摘录分开显示。

条目要限流。评论区咨询一篇能列十几条，不限的话「写文案时」和「必须写的保留意见」会被挤到面板最底下，那种注解等于没写。所以每类都有配额，voice 最多 3 条，core 最多 3 条。

## 图谱为什么不预存笔记之间的边

同地区几百篇笔记两两相连是 O(n²)，一个「海南」就能生成五万条边，既算不动也看不出东西。

所以边只有一种：笔记 ↔ 概念。看邻居时现算一跳：给定「三亚保利瑰丽」，取它连的笔记；给定一篇笔记，取它的概念，再取这些概念下度数最高的几篇兄弟。这样规模永远可控，语义也更准——反向链接会明确告诉你「跟这篇共享了 4 个概念：P2 房型不符、工具承诺、海南」，而不是「这两篇都在海南所以相关」。

三个坑：

酒店名必须归一化。「三亚保利瑰丽酒店（international，瑰丽集团）」和「三亚保利瑰丽（international）」是同一家，不归并的话图谱里全是孤点。

副本必须折叠。同一篇笔记常在多份快照里各存一份，不折叠的话一个酒店下面会挂四个同名节点，点开发现是同一篇——这比没有图谱更糟。

导出快照不进图。`raw_data`、`全量素材原文` 这类文件是数据转储不是笔记，连上去只会让节点下面挂一堆看不出规律的东西。

## 已知的弱

超长汇总文件（一个 md 装几百篇）拆不细。目前当成一篇处理，检索只能命中段落，元数据只有文件级的。

跨设备同步没做。SQLite 文件拷过去能用，但两边同时写会冲突。

语义检索要配外部接口，纯离线环境用不了，只能靠关键词。

图片和视频不进库。写「泳池长什么样」这类内容时，知识库帮不上，还是得自己看图。

概念图只认词表里的人群痛点。taxonomy 没覆盖的人群（比如「带老人」「宠物友好」）不会自动变成节点，得手工加别名。

早期几期采集记录是另一种格式（`### 1. 酒店名` 加 `pros:` / `cons:` 字段块），注解解析只认 `——` 那种写法，所以那几期的点评没进库。要补的话得给 `parse_daily_reviews` 加一个分支。

这些都在 issue 列表里，欢迎接手。
