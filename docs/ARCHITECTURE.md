# 架构与取舍

## 数据怎么流

```
资料库目录（md/docx/pdf/xlsx/txt）
      │  jiulv ingest：只读扫描，按 mtime + 内容哈希做增量
      ▼
解析 → 元数据抽取 → 分块
      │
      ├── docs      一篇一行：标题、类型、地区、酒店、等级、赞藏评、原文
      ├── chunks    按标题切段，700 字上限，80 字重叠
      ├── hooks     「## H-xxx-001」块解析成结构化钩子
      └── docs_fts / chunks_fts   FTS5 + 中文二元分词
      ▼
检索（BM25 → 聚合到文档 → 去重 → 排序）
      │
      ├── REST  /api/v1/*
      └── MCP   stdio，七个工具
      ▼
组稿：规则 + 钩子 + 同地区爆款结构 + 可核对事实 → 一段带约束的提示词
      ▼
Agent / 人写稿 → 发布 → 回填数据 → 复盘哪类钩子有效
```

## 为什么是 SQLite

单文件、能拷走、能离线、并发读没问题。这个场景的数据量级是几千到几万篇，全文检索用 FTS5 足够，上 Postgres 或向量库属于给自己增加运维负担。

代价是写并发弱。当前实现是每次请求开一个连接，写入只发生在收录和回填，量很小，WAL 模式下不会互相卡。

## 为什么自己做中文分词

FTS5 自带两个能用的选择，都不合中文场景：

- `unicode61` 按空白和标点切，中文整段当一个词，「三亚」搜不到「三亚文华东方」里的内容。
- `trigram` 按三字符切，查询必须三个字符以上，「瑞吉」「柏悦」这种两字词直接搜不到。

所以自己做一层二元组：中文连续串切成相邻两字的所有组合，英文数字整段保留。建索引和查询用同一个函数，词表天然一致。不需要 jieba 那种词典，也没有新词漏切的问题。

代价是索引膨胀，实测 1500 篇 2100 万字原文，索引库 115MB，其中分词索引占大头。这个体量完全可以接受。

## 排序

BM25 打分，做三处调整：

标题命中单独一路召回，给 2.0 的固定加分，因为标题命中通常比正文命中更相关。

按类型加权。`index` 类文件（全量索引、素材清单）动辄列几百个标题，BM25 很容易被它带偏，乘 0.4；`daily` 0.7；`ops` 和 `misc` 0.85；其余 1.0。

按等级加权。S 级乘 1.25，A 级 1.12。爆款本身是质量信号。

## 为什么要去重

真实资料库里同一篇笔记常有三四份：主素材库一份，OpenClaw 每次导出一份，全量快照里还有一份。全都显示出来，前十条结果可能只有三个不同内容。

处理方式是结果层折叠：标题归一化后相同、且类型相同的，只保留分数最高的那份，其余计数。原始文件一个不删，路径照旧可查，只是不占版面。

按标题而不是按正文哈希，是因为不同来源的导出会带不同的头部字段，正文哈希必然不同，但标题通常一致。

## 组稿为什么拼提示词而不是直接生成

有三个原因。

一是可核对。返回的每个片段都带来源路径和入选理由，写完能对着原文逐条查。

二是模型无关。同一份提示词给 DeepSeek、Claude、本地模型都能用，不需要为每个模型写一套 prompt。

三是省钱。生成交给 Agent 自己做，服务端不重复调一次模型。

如果确实要服务端直出，`generation.enabled: true` 配好就能用，但对多数人没必要。

## 素材挑拣的顺序

组稿时素材不是按检索分数堆的，按可靠性排：

参考篇目先取同酒店，再取同地区按等级和评论数排，都不够才用关键词兜底。每条带 `reason` 说明来源。

规则只取标题或路径里带「规则」「手册」「风格」「模板」「原则」的，避免把范文误当规则塞进去。

事实只取类型是 `fact` 或 `guide` 的，同酒店优先。如果取到的是别家酒店的，提示词里会明确写「只参考写法，事实不能挪过来」。

钩子按人群命中、痛点命中、类型命中、是否已验证四级排序，最匹配的放前面。

## 上下文包的结构

七段，顺序有讲究：

任务、硬规则、风格规则、钩子、爆款结构、事实清单、输出要求。

硬规则放前面是因为模型对开头的指令更敏感。事实清单放后面，紧挨着输出要求，减少长上下文里被稀释。输出要求最后压一句「正文后列出事实出处」，逼模型自己完成一次核对。

## 已知的弱

超长汇总文件（一个 md 装几百篇）拆不细。目前当成一篇处理，检索只能命中段落，元数据只有文件级的。

跨设备同步没做。SQLite 文件拷过去能用，但两边同时写会冲突。

语义检索要配外部接口，纯离线环境用不了，只能靠关键词。

图片和视频不进库。写「泳池长什么样」这类内容时，知识库帮不上，还是得自己看图。

这些都在 issue 列表里，欢迎接手。
