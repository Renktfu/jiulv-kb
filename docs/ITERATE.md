# 迭代说明：新笔记怎么进来

这份只讲一件事：你在 OpenClaw 或 WorkBuddy 那边产出了新东西，怎么让它变成库里能检索的内容。

先给结论，三句话：

新笔记写在**已连的目录**里，两分钟内自动进库，你什么都不用做。

新笔记写在**没连的目录**里，连一次，之后同样自动。

不想等，跑一条 `jiulv sync`。

---

## 二、新笔记落在哪才会被自动发现

规律很简单：**只要落在这十五个目录的任何一处，就会被扫到。**

日常最常用的三个位置：

写完一篇新笔记，放 `~/.openclaw/workspace/projects/xhs-archive/正文/`。命名跟着现有的来，`{点赞数}赞-{标题}.md`，头部写上发布时间和四个数：

```
- 发布时间：2026-10-28 21:30
- 观看：12000　点赞：860　收藏：1300　评论：90
```

赞数会自动换成等级：500 以上 S，100 以上 A，30 以上 B，不到 30 不标级，按等级排序时排在后面。

agent 的成稿，放对应的 `workspace-xhs-*`。写手放 `xhs-writer`，审完的放 `xhs-reviewer`，定稿放 `xhs-final`。

要让某个 agent 直接写进库，让它调 `POST /api/v1/inbox`，落进 `data/inbox/inbox_note/<日期>/`，同一分钟就能搜到。

## 三、三种触发方式

**什么都不做。** `jiulv start` 起的不只是一个网页，还有个同步线程，每 120 秒扫一次。指纹没变就整轮跳过，开销可以忽略。所以放进去之后最迟两分钟，页面上就能搜到。

**立刻同步。** 等不了两分钟就跑：

```bash
jiulv sync
```

它会把十五个来源都过一遍，只处理有变化的。刚才实测一次全量扫，无变化时 0.2 秒，进 118 篇是 2.8 秒。

**只同步一个来源。** 知道是哪个库变了，指定它更快：

```bash
jiulv sync --source "OpenCLaw 笔记归档"
```

页面上也有，来源页那个手动同步按钮，背后就是 `POST /api/v1/sync`。

---

## 四、接一个新目录

三种做法，按场景挑。

**自动探测（推荐）。** 不知道有哪些库可连，让程序自己找：

```bash
jiulv connect
```

它会扫本机标准位置的 WorkBuddy 和 OpenClaw 目录，把找到的写进 `sources.yaml`，已有的不会重复加。

**只接某一类。** 比如只想加笔记归档：

```bash
jiulv connect --only oc-archive
```

profile 名字用 `jiulv connect --dry-run` 先看一眼。

**手写。** 目录不在标准位置，或者不想让它被自动探测影响，直接在 `config.yaml` 的 `sources` 下加一条。手写优先级最高，`sources.yaml` 里同路径的会被忽略：

```yaml
sources:
  - name: 我的新笔记
    group: mine
    path: ~/Documents/我的文案
    include: ["**/*.md", "**/*.txt"]
    exclude: ["**/.*/**"]
```

**改完不用重启服务。** 同步线程每轮开始前会重读一次配置，日志里会打一行「配置变了：15 → 16 个来源」和新增的名字。以前只在启动时读一次，新接的目录要等到重启才生效，很容易以为接失败了。

## 五、怎么确认真的进来了

四个地方，从粗到细。

**来源页。** 每个来源后面有篇数，还有「上次扫描」时间。刚同步过的会显示当前时间。

**命令行。** 一行看全库：

```bash
jiulv stats
```

**检索。** 拿新笔记里独有的一句话去搜。这是最硬的验证，搜得到才算真进了：

```bash
jiulv search "索菲特 房型 房号"
```

命中第一行会带等级、赞藏评和来源目录。刚才那篇就是从 `OpenClaw 笔记归档` 里搜出来的。

**看这次进了什么。** 要具体数字用 `--json`：

```bash
jiulv sync --json | python3 -m json.tool
```

它会给出 `added`、`updated`、`removed` 三个数，以及是哪几个来源有变化。

## 六、改过的文件会重新解析

同一个文件改了内容，下一轮同步会认出指纹变了，重新抽取元数据、重新分块、重算这篇的注解。不用手动 `--rebuild`。

只有两种情况需要重建：改了 `jiulv/extract.py` 这类解析逻辑，或者一次动了几百个文件。那时候：

```bash
jiulv ingest --rebuild
```

1500 篇大约一分钟。

---

## 七、删掉和停用的区别

源目录里删了文件，下一轮同步会把对应的文档从库里移除。原始文件你删了，库里也跟着没了，这是预期行为。

**停用一个来源是另一回事。** 在 `sources.yaml` 里给某条加 `enabled: false`，它就不在来源列表里了，那批文档会在下一轮被判为「来源已删除」然后从库里清掉。想临时排除一批内容又不想丢索引，别停用来源，把目录里的文件移走再移回来也要重建。

确实要停用，就接受这个代价：重新启用后要重新收录一遍。

## 八、今天踩过的四个坑

写在这里，下次遇到能对上。

**`connect --only` 把其他来源清空了。** 原来的实现拿「本次新连的」直接覆盖 `sources.yaml`，于是带 `--only` 连一条，剩下的十几条全没了。现在改成和原有条目合并。如果你在旧版本上用过 `--only`，检查一下 `sources.yaml` 是不是只剩一条，是的话跑一次不带参数的 `jiulv connect` 就能补回来，已入库的文档不受影响。

**配置文件写坏了会清库。** 旧版本读 `sources.yaml` 解析失败时当作「没有来源」处理，下一轮同步就按来源已删除把文档全清掉。现在解析失败会拒绝加载、保留上一版配置，日志里打「重读配置失败，继续用上一版」，同步照常用旧配置跑。手改 YAML 缩进搞错不会再变成事故。

**归档笔记的互动数据读错位。** 归档用的写法是「观看：4501　点赞：103　收藏：177」，单位在前面。旧解析器只认「103赞」这种数字在前的写法，于是把 4501 当成点赞、103 当成收藏，整篇数据错一层。现在两种写法都认，还会先抹掉日期再解析，免得 `2026-06-16` 里的 `16` 被当成点赞数。

**新笔记没有等级，排序时沉底。** 人工分级只存在于老资料库里，新归档没标等级，按等级排序永远排最后。现在按点赞数兜底推等级。索引页例外，它罗列全库数据，按点赞推会推出一个假的 S 级，所以索引页不推等级。

## 九、建议的日常节奏

早上开始干活前跑一次 `jiulv sync`，把昨晚 OpenClaw 跑出来的东西收进来，顺便确认来源篇数没有异常。

写稿时用组稿（页面上的组稿页，或 agent 里的 `kb_context_pack`），它取的是库里最新的内容，不用手动喂资料。

成稿发出去之后，用 `POST /api/v1/feedback` 把数据回填。回填记录会进 `outcomes` 表，下次组稿时能被参考，这是让库越用越准的那一步。

每周看一眼来源页，确认十五个来源都还在、篇数没有归零。路径被移动或改名是最常见的故障，`jiulv doctor` 能直接指出哪条断了。

## 十、几个具体问题

**新笔记进了库，但搜不到。**
先看来源页那个来源的篇数变没变。没变就是路径问题，`jiulv doctor` 查。变了但搜不到，可能是标题和旧笔记重合，被当成副本折叠了，卡片上会写「另有 N 份副本」。要逐条看，接口传 `dedupe=false`。

**同一个目录被连了两次，篇数翻倍。**
`config.yaml` 和 `sources.yaml` 里各有一条指向同一个目录。按路径判重用的不是字符串比较，`~/x` 和 `/Users/你/x` 会被认成同一个，但大小写和软链接的情况仍可能漏。检查两份配置，删掉一条。

**服务在跑，但我改了 `sources.yaml` 没反应。**
下一轮同步才会读到，最迟两分钟。急的话跑一次 `jiulv sync`，它每次都会重读配置。

**想接入的目录很大，几千篇，会不会很慢。**
首次收录大约每百篇两秒，两千篇一分钟左右。之后是增量，没变化时整轮 0.2 秒。慢的是首次建索引和算注解，一次性的。

**能不能只让某个来源不进检索。**
目前没有这个开关。替代做法是把文件从目录里移走。如果这个需求常用，可以在 `config.yaml` 里给来源加 `enabled: false` 再配合另一条指向符合条件子目录的来源，但要注意停用会清掉那批索引。
